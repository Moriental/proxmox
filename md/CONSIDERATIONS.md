## Jenkins 별도 VM (가이드 전달, 실행 미확인)

**결정**: k8s 클러스터 안에 파드로 띄우는 대안(리소스 절약)도 검토했으나, "실무에서도 CI/CD 서버는 따로 띄운다"는 이유로 **별도 VM**으로 진행하기로 결정.

**가이드 요약**:
- 기존 cloud-init 템플릿(9000)에서 클론 (VM ID 104, IP `192.168.1.104`)
- 최소 스펙: 2vCPU / 2GB RAM (리소스 빠듯해서 최소치)
- Java 17 + Jenkins 공식 apt 저장소로 설치
- 초기 비밀번호: `/var/lib/jenkins/secrets/initialAdminPassword`

**미확인**: 실제로 VM 생성/설치까지 진행했는지 대화상 확인 안 됨. 진행 시 `PROGRESS.md` Phase 1 섹션에 흡수.

## RAM 증설 (구매 방향만 결정, 미구매)

**현재 구성 확인됨**: `dmidecode -t memory` 결과 — Samsung DDR4-2666 8GB × 2 (Part Number `M378A1K43CB2-CTD`), ChannelA/B에 각 1개씩 장착, **빈 슬롯 2개 있음**(ChannelA-DIMM0, ChannelB-DIMM0). 교체 없이 추가만 하면 됨.

**결정 과정**:
- 처음 8GB 추가 검토 → 가격 부담(DDR4 가격 급등 시기, `proxmox-homelab-troubleshooting.md` 2-1 참고) 때문에 보류
- 4GB로 축소 검토 → 확정. DDR4-2133(느린 속도) 구매도 검토 중 — 속도가 기존 2666에서 전체 다운클럭되어 대역폭 약 20% 감소하지만, VM 호스팅 워크로드는 대역폭보다 **용량**이 중요해서 감수하기로 함
- 구매 전 확인할 스펙: DDR4, 논ECC UDIMM, 2666MHz 이상(또는 2133도 용량 우선이면 허용)
- 가격 대란 시기 고려해 중고 마켓(당근마켓 등) 키워드 알림도 옵션으로 제안됨 (SSD 살 때 썼던 전략과 동일)

**+4GB(20GB) 확보 시 활용 계획**:
- 호스트 여유분을 그냥 두지 말고 워커 VM(102, 103) RAM을 4GB→6GB로 증량하는 데 사용 권장 (Longhorn 등 클러스터 내부 워크로드가 워커 VM 할당량 안에서 돌기 때문)

**미실행**: 아직 구매 전.

## Longhorn (분산 스토리지) — 검토만, 미설치

**결론**: 별도 VM 불필요, 기존 워커 노드에 DaemonSet으로 설치됨 (ArgoCD/Calico와 같은 방식).

**리소스 추정**:
- longhorn-manager + instance-manager + ui + CSI 사이드카 합쳐서 **노드 2~3대 기준 약 1~1.5GB**
- 볼륨 데이터는 기본 **3중 복제** → 디스크 공간도 별도로 소모 (지금 워커 디스크 20GB 기준 부족해질 수 있음)

**전제 조건**: 각 노드에 `open-iscsi` 설치 + iscsid 활성화 필요.

**절충안 제안**: 기본 레플리카 3개 → **2개로 축소**(`defaultSettings.defaultReplicaCount: 2`)해서 RAM/디스크 부담 완화. RAM 증설(위 항목) 이후 진행 권장.

**로드맵 연결**: Phase 4(관측성 스택)의 PV 요구사항과 묶어서 도입하는 게 자연스러움 — Prometheus/Grafana/Loki가 파드 재시작에도 데이터를 잃지 않게 하는 목적과 직접 연결됨.

## PV/StorageClass 필요성 (사전 확인 필요, 미설치)

kubeadm 클러스터에는 **기본 StorageClass가 없음** (`kubectl get storageclass`로 확인 가능, 아마 빈 목록). Prometheus/Grafana/Loki 전부 기본값이 `emptyDir` 또는 persistence 비활성이라, PVC 없이 설치하면 **파드 삭제/재스케줄 시 데이터 유실**.

**선택지 비교**:
| 방법 | 장점 | 단점 |
|---|---|---|
| local-path-provisioner (추천, 우선 도입) | 설치 간단, 가벼움 | 볼륨이 특정 노드에 고정 (지금 규모엔 문제 없음) |
| NFS + nfs-provisioner | 노드 무관 포터블 | 별도 서버 필요, 단일 장애점 |
| Longhorn | 노드 간 복제로 진짜 이중화 | 리소스 부담 큼 (위 항목 참고) |

**미실행**: Phase 4 착수 전에 최소 local-path-provisioner는 먼저 깔아야 함.

## PLG 스택 + Istio 동시 구동 가능성 — 계산만 해봄, 결론은 "동시엔 무리"

**리소스 추정치**:
- PLG(튜닝 시): ~1.5~2GB / 기본값: ~3~4GB
- Istio 컨트롤플레인: ~1~1.5GB + **사이드카 파드당 +50~100MB** (메시에 넣는 서비스 늘수록 계속 증가)
- 워크로드용 실사용 가능 용량(워커 2대 기준): 약 8GB

**결론**: 둘 다 기본값으로 상시 가동은 불가능 (최소 4GB+가 필요한데 남는 여유가 부족). 대안:
1. **Istio 대신 Linkerd** — 사이드카가 Envoy 대비 훨씬 가벼움 (`ROADMAP.md` Phase 3에 이미 반영된 결정과 일치)
2. Istio를 꼭 쓰고 싶으면 **Ambient 모드**(사이드카 없이 노드당 ztunnel 하나) 검토
3. 그래도 안 되면 "필요한 것만 켜기" 원칙대로 순환 운영

**미결정**: Istio vs Linkerd 최종 선택은 Phase 3 착수 시점에 다시 결정하기로 함.

## Proxmox 멀티 노드 클러스터링 — 검토 후 보류

Datacenter 밑에 노드를 여러 개 두려면 물리적으로 별개인 서버가 필요 (`pvecm` 클러스터링). 지금은 PC 1대뿐이라 의미 없음. Nested 가상화로 가짜 2번째 노드를 만드는 것도 검토했으나:
- 물리적으로 동일 하드웨어라 진짜 HA 효과 없음
- RAM만 추가로 소모

**결론**: 유휴 PC를 한 대 더 확보하기 전까지는 보류.
