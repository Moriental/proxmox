# Proxmox 홈랩 구축 트러블슈팅 가이드

> 오래된 데스크탑(i5-4570)으로 시작해 i5-8400 PC로 전환, Proxmox + Kubernetes 홈랩을 구축하는 과정에서 겪은 문제와 해결 기록.

---

## 1. 하드웨어 사양 문제

### 1-1. CPU-RAM 세대 불일치 의심
- **증상**: i5-4570(하스웰, DDR3 전용) 보유 중인데 "DDR4 8GB"라고 알고 있었음.
- **원인**: i5-4570은 LGA1150 소켓으로 DDR3만 지원. DDR4라면 CPU가 다른 모델일 가능성.
- **해결**: CPU-Z로 실제 메인보드/CPU/램 규격 확인 필요. (최종적으로는 이 PC 대신 더 사양 좋은 i5-8400 PC를 쓰기로 전환)

### 1-2. 8GB RAM으로 OpenStack/K8s 실습 한계
- **증상**: DevStack 올인원 구성 시 컨트롤 플레인만으로 RAM 5~6GB 소모.
- **원인**: Keystone, Nova, Neutron, Glance, Placement, MariaDB, RabbitMQ 등이 개별 프로세스로 상주.
- **결론**: 8GB는 최소 동작만 가능, 모니터링 스택(Prometheus/Grafana)이나 여러 인스턴스 실행은 불가능. 최소 12~16GB 권장.

### 1-3. HDD 사용 시 etcd 장애
- **증상**: (사전 검토 단계) HDD로 etcd/분산 스토리지 운용 시 fsync 지연으로 클러스터 불안정 예상.
- **원인**: etcd는 쓰기마다 fsync 호출. HDD의 fsync 지연(10~20ms)이 `apply entries took too long`, `failed to send out heartbeat on time` 등 경고를 유발하며 리더 선출 반복 실패로 이어짐.
- **해결**: SATA SSD 필수 확보 (SSD의 fsync 지연은 1ms 이하 수준).

## 2. 부품 구매 관련 트러블슈팅

### 2-1. 메모리/SSD 가격 급등 시기와 겹침
- **증상**: 2026년 기준 DDR5/DDR4 SO-DIMM, NVMe SSD 가격이 대란 수준으로 급등. 애초 안내했던 시세(SSD 6~8만원)가 실제로는 30만원대로 틀림.
- **원인**: AI 수요로 인한 메모리·낸드 공급 부족, NAND 생산라인 가동 축소.
- **해결**:
  - SATA SSD는 NVMe 대비 가격 상승폭이 낮음(SATA +12% vs NVMe +60%대) → SATA로 방향 전환.
  - 신품 미니PC(50만원대)보다 중고 부품(DDR3 램 + SATA SSD) 조합이 훨씬 저렴.
  - DDR3는 이번 대란과 무관해 가격 안정적.

### 2-2. 검색으로 찾은 매물이 대부분 품절
- **증상**: 검색 결과 링크로 들어가면 "구매불가" 표시.
- **원인**: 오픈마켓 특성상 개별 중고 매물은 검색엔진에 오래 남아있지만 실제 재고는 이미 소진된 경우가 많음. 리퍼몰도 소량 입고라 금방 품절.
- **해결**:
  - 카테고리 페이지에서 직접 필터링(가격대, 최신순/판매량순) 후 확인.
  - "바로발송" 표기 확인.
  - 개인 중고(당근마켓 등)는 키워드 알림 걸어두고 기다리는 방식이 효율적.

### 2-3. 저가 SSD의 품질/신뢰도 판단
- **증상**: 여러 SSD 후보(WD Green, 팀그룹 CX2, FORESEE 등)를 두고 신뢰도 판단 어려움.
- **핵심 판단 기준**:
  - DRAM 탑재 여부 (없어도 실습 용도로는 크게 문제 없음, 다만 랜덤 쓰기 성능 저하)
  - 화이트라벨/OEM 임베디드 제품(FORESEE 등)은 스펙 비공개·A/S 부재로 비권장
  - 리뷰 없음 자체는 문제 아님(오픈마켓 특성) — 대신 판매자의 사업자 정보, 만족도, 에스크로 여부로 판단
  - 리테일 브랜드(삼성, 팀그룹 등)면 신품/중고 모두 무난

### 2-4. 용량 계산 오류(과대평가 → 과소평가 왔다갔다)
- **증상**: 처음엔 "240GB 필요"라고 안내했다가, 이후 재계산 결과 실사용 40GB면 충분하다고 정정.
- **교훈**: Proxmox(호스트 10~15GB) + VM 3대(약 25GB, thin provisioning 기준) = 실사용 약 40GB. 120GB로도 충분히 운용 가능하나 여유는 크지 않음(스냅샷은 원본과 같은 볼륨에 생성되므로 별도 디스크로 분리 불가 — 이 부분 최초 안내가 부정확했음).

## 3. 네트워크 구성 트러블슈팅

### 3-1. Wi-Fi로는 Proxmox 브리지 구성 불가
- **증상**: PC가 무선 랜카드로 인터넷에 연결된 상태에서 Proxmox를 쓰려는 시도.
- **원인**: Proxmox VM은 호스트의 리눅스 브리지(vmbr0)에 연결되어 각자 별도 MAC 주소로 통신. 802.11 무선 표준은 클라이언트가 자신의 MAC 하나로만 통신 가능하므로, VM의 MAC으로 나가는 프레임을 AP가 폐기. 결과적으로 브리지 자체가 동작 안 함(MetalLB L2 모드도 불가).
- **해결**: 반드시 유선(이더넷) 연결 필요.

### 3-2. 여분 랜선 없음 + 공유기와 PC가 다른 방
- **증상**: 유선 연결에 필요한 랜케이블이 집에 없고, 공유기와 서버가 물리적으로 떨어진 방에 위치.
- **검토한 대안**:
  1. PC를 공유기 방으로 이동 (헤드리스 서버 운용 특성상 가장 간단)
  2. 문틈용 납작 랜케이블 설치
  3. 유휴 공유기를 무선 브리지/리피터로 활용
  4. 전력선통신(PLC) 어댑터
- **최종 선택**: 유휴 ipTIME 공유기를 PC 방으로 가져와 무선으로 메인 공유기에 연결(확장) 후 PC와 유선 연결.

### 3-3. 비상용 랜케이블 불량(링크 점멸)
- **증상**: 케이블 연결 시 포트 LED가 한쪽만 잠깐 들어왔다 꺼짐. 링크가 유지되지 않음.
- **원인 추정**: 케이블 내부 단선 또는 커넥터 접촉 불량(8가닥 중 일부만 연결되어 기가비트 협상 실패, 100Mbps로도 불안정).
- **해결**: 새 케이블(CAT.6)로 교체 권장. 저렴한 소모품이므로 진단에 시간 쓰지 않고 교체가 효율적.

### 3-4. ipTIME 공유기 인터넷 연결 안 됨
- **증상**: 관리 페이지(192.168.0.1) 접속은 되나 외부 통신 불가.
- **원인**: 공유기를 물리적으로 이동시키면서 인터넷 회선(벽 단자)과 분리된 상태. 공유기는 회선을 만들어내는 장비가 아니라 나눠주는 장비이므로 상위 연결이 없으면 인터넷 자체가 불가.
- **해결**: 무선 확장(브리지/리피터/WDS) 모드로 전환하여 메인 공유기의 Wi-Fi를 통해 인터넷을 받아오도록 설정.

### 3-5. 관리자 비밀번호 변경 후 로그인 불가
- **증상**: ipTIME 비밀번호를 변경한 후 로그인 화면까지는 뜨지만 인증 실패.
- **원인 추정**: 관리자 계정과 Wi-Fi 계정 설정을 혼동했을 가능성, 또는 아이디까지 같이 변경됐을 가능성.
- **해결**: 기본 계정(admin/admin) 및 신규 비밀번호 순차 시도 → 실패 시 리셋 버튼(10초 누르기)으로 공장 초기화 후 무선 확장 설정 재구성.

### 3-6. IP 대역 자동 변경 → 이중 NAT 발생
- **증상**: "내부 IP 주소를 자동으로 변경하시겠습니까?" 안내에 따라 자동 변경 진행.
- **원인**: 메인 공유기(192.168.0.x)와 ipTIME(기본값 192.168.0.1)의 IP 대역 충돌을 감지하여 ipTIME이 자신의 내부 대역을 192.168.1.x 등으로 자동 변경. 이는 ipTIME이 **공유기(라우터) 모드**로 동작 중이라는 의미(브리지/AP 모드가 아님).
- **영향**:
  - 이중 NAT 구조 형성 (메인 공유기 대역과 Proxmox가 속한 대역이 분리됨)
  - 다른 대역(예: 192.168.0.x)에 있는 기기에서 Proxmox 웹 UI(192.168.1.x) 접속 불가
  - 포트포워딩이 필요할 경우 양쪽 공유기에 각각 설정해야 하는 번거로움 발생
- **현재 상태**: Proxmox 설치 및 로컬 실습 자체에는 지장 없음(같은 대역 내 통신은 정상). 다만 외부/타 기기 접속 시 대역 일치 여부 확인 필요.
- **향후 개선 방향**: 필요 시 ipTIME을 AP(브리지) 모드로 전환하여 단일 대역으로 통합. 외부 노출은 Cloudflare Tunnel 등을 활용해 이중 NAT 영향을 우회하는 방법도 고려 가능.

## 4. Proxmox 설치 트러블슈팅

### 4-1. USB 굽기 시 ISO/DD 모드 선택
- **증상**: Rufus에서 "이 이미지는 ISO/파일 복사 모드와 호환되지 않아 DD 이미지 쓰기 모드가 적용된다"는 안내 메시지.
- **설명**: Proxmox ISO는 하이브리드 이미지이나 제작사가 ISO 모드 호환을 보장하지 않음. **DD 모드가 정상 동작 방식**이며, ISO 모드로 구우면 부팅 실패 가능성.
- **해결**: 안내된 대로 DD 모드 그대로 진행.

### 4-2. 구운 USB가 드라이브 2개로 인식됨
- **증상**: 탐색기에서 USB 하나가 서로 다른 드라이브 문자 2개로 표시.
- **원인**: DD 모드로 구운 Proxmox 이미지 안에 부팅용 파티션과 소용량 데이터 파티션이 함께 존재하는 하이브리드 구조. 정상 현상.
- **해결**: 탐색기에서 포맷 요청이 뜨더라도 무시. 부팅 테스트로 정상 여부 확인.

### 4-3. 유료 저장소(enterprise repository) 미인증 오류
- **증상**: 로그인 시 "이 서버에 대한 유효한 구독이 없습니다" 팝업. `apt update` 시 `401 Unauthorized` 오류.
- **원인**: Proxmox 기본 설치는 유료(enterprise) 패키지 저장소로 설정되어 있어, 구독 키가 없으면 인증 실패.
- **해결**:
  1. 기존 유료 저장소 파일 비활성화
     - PVE 9.x는 `.list`가 아닌 `.sources`(deb822 포맷) 형식 사용 → `pve-enterprise.list`가 아니라 `pve-enterprise.sources`로 존재
     - 파일명을 `.disabled`로 변경하거나 내용 주석 처리
  2. 무료 저장소(`pve-no-subscription`) 추가:
     ```
     cat > /etc/apt/sources.list.d/proxmox.sources << 'EOF'
     Types: deb
     URIs: http://download.proxmox.com/debian/pve
     Suites: trixie
     Components: pve-no-subscription
     Signed-By: /usr/share/keyrings/proxmox-archive-keyring.gpg
     EOF
     ```
  3. `apt update && apt dist-upgrade -y`

### 4-4. Ceph 저장소도 별도로 유료 인증 필요
- **증상**: `pve-enterprise` 저장소를 비활성화한 후에도 `ceph-squid` 저장소에서 동일한 401 오류 지속.
- **원인**: Ceph(분산 스토리지 기능) 패키지도 별도의 엔터프라이즈 저장소로 관리되며, 이 역시 구독 없이는 접근 불가.
- **해결**: 단일 노드 구성에서는 Ceph 사용 계획이 없으므로 해당 저장소 파일도 `.disabled`로 이름 변경하여 비활성화. (향후 노드를 3대 이상으로 확장하고 분산 스토리지/고가용성 실습을 하게 되면 그때 Ceph 무료 저장소를 별도로 구성 가능)

## 5. 앞으로 남은 작업 / 참고 사항

- [ ] 웹 UI 브리지(vmbr0) 및 유선 NIC 연결 상태 확인
- [ ] Ubuntu Cloud-Init 이미지로 VM 템플릿 제작
- [ ] kubeadm 기반 3노드 클러스터 구성 (컨트롤 플레인 1 + 워커 2)
- [ ] CNI는 Flannel로 시작 (저메모리 환경에 유리), 여유 생기면 Calico로 전환
- [ ] MetalLB + ingress-nginx 구성 (베어메탈 LoadBalancer 실습 포인트)
- [ ] Terraform(bpg/proxmox provider) + Ansible로 IaC 파이프라인 구축
- [ ] 관측성 스택은 ELK 대신 Prometheus + Grafana + Loki 조합 권장(리소스 훨씬 절약)
- [ ] 서비스 메시는 Istio보다 Linkerd가 저사양 환경에 적합
- [ ] 필요 시 ipTIME을 AP(브리지) 모드로 전환하여 이중 NAT 해소
- [ ] 외부 접속이 필요해지면 Cloudflare Tunnel + Access 검토 (포트포워딩보다 안전, 이중 NAT 영향 우회 가능)
